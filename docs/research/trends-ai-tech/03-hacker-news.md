### Cluster C: Actors / Durable Objects as infrastructure (the host's own Show HN)
- **"Show HN: Durable Actors – OSS Durable Objects with configurable compute"** (TerseAI, the host), 53 / 25 (Oct 6) [49980399](https://news.ycombinator.com/item?id=49980399). This is the only story in the window matching "durable objects". What the post itself says (verified): each actor is "a tiny server that handles one request at a time and has its own SQLite database", addressed by name, "perfect primitive for deploying multiplayer agents"; users connect to it over websocket; it is MIT-licensed and ships a Helm chart. **Added at verification:** the post gives its own p95 numbers: "Durable write: 85.6ms", "Stateful Read (data in sqlite): 2.14ms", "Actor Warm up: 334ms". It links a live counter demo at `https://demo.useterse.ai/`, makes the CRM data-race pitch itself ("you can protect critical data such as a CRM and allow multiple agents to run concurrently without worrying about data races"), and promises a SQLite-table export "via CLI + MCP". Later in the thread the founder says durability uses "GCS rapid or other cloud technology". GitHub (`gh repo view`, 2026-10-29): `TerseAI/durable-actors` has **291 stars and 22 forks**, MIT license, was created 2026-08-30, and was pushed to within the last hour. Questions the founders got and their answers:
  - *vs Temporal / Azure Durable Functions / AWS Lambda Durable*: co-founder olism says Durable Actors handles "durable state, not durable execution" and calls it "more similar to cf durable objects or orleans". thomask1995 reposted it because it appeared suppressed. At re-check, olism's original comment is visible in the API too.
  - *State query across actors* (jeremycarter): "one of the common problems with the virtual actor model is state query". thomask1995 agrees and mentions plans to sync to a data lake.
  - *Write latency*: anilgulecha says "100ms for a write - not usable for anything beyond toys" and points to `denoland/celld`, where he claims "Durable writes there are as low as 1ms". thomask1995 replies that celld's single-node durable write ("wait for bucket") is 90ms, "Documented pretty clearly on the landing page". anilgulecha pushes back hard (1ms with 2 VMs in the same AZ) and the founder asks for a reproducible setup. The exchange ends unresolved, so the latency objection still stands.
  - *vs Rivet / celld*: the founder says the API is closer to Cloudflare's and modeled on Swift actors (he spent 7 years writing Swift at Apple). Differentiators he lists: per-actor-class CPU/RAM set with a decorator, running in sandboxes, TS/Python SDKs, generated type-safe clients. Another commenter (divyagnan) asked whether self-hosting is possible outside GCP. The founder's in-thread reply only says "We are pretty opinionated on how to host these" plus the Helm chart. **Resolved at verification from the README:** local development runs with one command (`bunx durable-actors init` / `bunx durable-actors dev`, Bun 1.4.2+ required), and the documented self-host path is "self-host the Durable Actors runtime on GCP" (`docs/self-hosting.md`). Non-GCP self-hosting is not documented. The README quickstart is a multiplayer AI chat actor using `@Persisted`, `@Interleave`, `broadcast()` and the Vercel AI SDK with `openai(...)`.

## 5. Hackathon implications
1. **Pitch the build as "durable, multiplayer agents you can watch live"**, not as a new model or a coding copilot. HN's top AI-infra conversation in October is durable agents (Pi Durable, Omnara, Dots), and the open question people keep asking is "what are infinitely-running agents *for*?" Give a concrete answer on stage.
2. **The format with the strongest evidence is a swarm in a shared world.** YC Labs published Minecraft/Mindustry swarms *today* and the comments loved the emergent social stories. Halloween version: a haunted house or séance where each ghost or NPC is a Durable Actor (its own SQLite memory, one-at-a-time mailbox), ghosts gossip and conspire through Agent Relay, and players join over websocket. This uses both host products on purpose, which is the bonus the rubric asks for.
3. **Plan around the latency criticism.** HN commenters said reasoning LLMs make live games turn-based. Use the fast tiers (GPT-6 Luna or the cheapest OpenAI realtime/voice option available on your credits; confirm model names in the OpenAI research file). If you add voice, the whodunnitai Show HN is the template (gpt-realtime over WebRTC, one tool call per accusation, a cheap judge model) and also the warning (cost, a credit outage mid-thread, backlash over signup). Cap session length and pre-load credits. and a tick- or turn-based mechanic, so slowness becomes part of the design ("the spirits answer at midnight on each tick").
4. **Answer one objection from the Terse Show HN on stage.** (a) *State query across actors*: add a live "graveyard ledger" that mirrors actor state into Supabase Postgres + Realtime, which also pitches for the Supabase "scale to millions" prize. Or (b) *serialization*: show two agents racing to write the same record and the actor's one-request-at-a-time guarantee preventing the race. The founders brought up the CRM-race example themselves.
5. **Make agent-to-agent traffic visible.** Corgi's "running feed of agent activity" and the CPU-cache story show that people want to *see* agents talk. Render the Agent Relay message stream as a live transcript or graph, Ouija-board style. Include a permission boundary so it isn't another "rogue agent" story: some agents cannot message others. Alter's thread shows that memory leaking across privilege levels is the open concern.
6. **Copy the Show HN pattern for the demo:** one URL, opens with no signup, an immediate visual, a single playful hook. Avoid "vibe-coded template" looks; HN and probably judges treat them as a negative.
7. **Pre-event setup (before Oct 31):** install Bun 1.4.2+ and run `bunx durable-actors init my-actors && bunx durable-actors dev`, then `bunx durable-actors generate` for the typed client. The README's multiplayer-chat quickstart is close to a ghost-NPC actor already. Run locally on demo day; the only documented hosted path is GCP via Helm, which is too much to set up in 5 hours. Open `https://demo.useterse.ai/` to get a feel for the latency. Install the Agent Relay SDK/CLI (`AgentWorkforce/relay` on GitHub is the repo a founder-adjacent commenter cited). Pre-create the OpenAI and Supabase projects. Have a fallback in case actor writes take about 100ms (the published p95 is 85.6ms; batch state writes per tick).
8. **Don't** lead with "a new coding agent", "an agent multiplexer" or "a sandbox". HN shows all three are crowded categories within the current YC batches (Agent37, Herdr, Corgi, Omnara).
